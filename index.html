ASIC Implementation of a RISC-V Processor in 14-nm CMOS | Synopsys VCS / DC / ICC2 / PrimeTime

M.S. Applied Project (Thesis) • San Francisco State University • Spring 2026 • SAED 14-nm • 200 MHz target

Project Overview

Complete RTL-to-GDSII implementation of a 5-stage pipelined RISC-V CPU in a 14-nm CMOS technology, built entirely with the Synopsys EDA tool suite. RISC-V is an open-source instruction set architecture that allows customization without the licensing and IP constraints of proprietary ISAs such as x86 and ARM — a growing advantage as machine learning and AI workloads push more computation onto application-specific hardware. The design implements Instruction Fetch, Decode, Execute, Memory and Write Back stages with a hazard detection unit and a forwarding unit, and was carried through functional verification, logic synthesis, pre-layout static timing analysis, full physical implementation, and post-layout timing sign-off. This work migrates an earlier 32-nm SFSU implementation to a 14-nm FinFET library and to the IC Compiler II tool flow. Advised by Dr. Hamid Mahmoodi, with Dr. Zhuwei Qin on the defense committee.

Key Specs

• ISA: RISC-V, 32-bit instructions, 32 general-purpose registers
• Instruction formats: R, I, S, B and J, decoded from 8 custom 7-bit opcodes
• Pipeline: 5 stages (IF / ID / EX / MEM / WB) with IFID, IDEX, EXMEM and MEMWB registers
• Hazard handling: load-use hazard detection with pipeline stall, plus EX/MEM and MEM/WB forwarding
• Clock target: 5 ns period (200 MHz)
• Technology: Synopsys SAED 14-nm EDK (SLVT / LVT / RVT / HVT cells) at 0.88 V, 125 °C
• Data memory: 4096-entry × 32-bit array

What I Did

• Developed synthesizable Verilog RTL for the datapath, control unit, ALU, comparator, register file, forwarding unit and hazard detection unit
• Verified the design in Synopsys VCS and debugged cycle-by-cycle pipeline behavior in Verdi, exercising R-type, I-type, branch, jump, load and store instructions
• Synthesized to a gate-level netlist in Design Compiler against the SAED 14-nm library with a 5 ns ideal-clock constraint
• Ran independent pre-layout sign-off STA in PrimeTime and generated timing, power and area reports
• Completed the full ICC2 physical flow: design loading, floorplanning, PG ring and power network, placement, clock tree synthesis, and detail routing with post-route optimization
• Performed post-layout STA on the extracted netlist to confirm setup and hold closure with real parasitics and a propagated clock tree

Results

• Pre-layout setup slack: +3.88 ns MET (1.11 ns arrival vs. 4.99 ns required) — 78% margin at the 5 ns target
• Post-layout setup slack: +2.83 ns MET after placement, CTS, routing and parasitics
• Post-layout hold slack: +0.02 ns MET — no hold violations
• Area: 9,803.48 total cell area (4,659.03 combinational, 5,144.45 non-combinational), 28,226.24 total area
• Gate count: 20,943 cells (15,356 combinational, 5,520 sequential, 3,543 buf/inv) across 24,732 nets
• Power: 1.2118 mW total dynamic (1.1688 mW cell internal, 43.01 µW net switching)
• Zero timing violations at every sign-off point, with headroom left for further frequency scaling

Deliverables

Verilog RTL and testbench, VCS/Verdi verification results, Design Compiler synthesis scripts and gate-level netlist, PrimeTime pre- and post-layout timing reports, power and area reports, and the complete ICC2 physical implementation database (TOP_CPU_placed, TOP_CPU_cts, TOP_CPU_routed).

Facial Gesture Controlled Robotic Arm | EEG Brain-Computer Interface

ENGR 845 Human-Machine Interface • Emotiv Insight EEG + Arduino UNO • 3-person team project

Project Overview

A human-machine interface (HMI) that lets a person drive a robotic arm using facial gestures detected by an EEG headset. The system chains together data acquisition, signal interpretation, and control of an external actuator: an Emotiv Insight 5-channel wireless EEG headset streams over Bluetooth to a PC, gestures are classified against a trained profile, and the resulting commands are mapped to Arduino UNO pins that drive the arm's servos over PWM.

My Role

Team project with Dahlen Lakin and Michael Cabrera. I originated the project concept — using an EEG headset to control a robotic arm through an HMI — and did the initial research to determine which tools could actually make it work. That search turned up HITIBrain, the software that bridges the Emotiv headset to an Arduino board, which was the piece that made the whole integration feasible. I also sourced and acquired the robotic arm, verifying it met the mechanical and functional requirements for EEG-driven control. Michael led the testing phase, sourced the servos against torque and voltage requirements, and led documentation; Dahlen served as primary test subject and handled software licensing.

System Architecture

• EEG capture — Emotiv Insight, 5 channels, Bluetooth to host PC
• Training — EmotivBCI used to record a neutral baseline plus four gestures: smile, furrow brows, raise brows, clench teeth
• Bridge — HITIBrain selects a trained profile and maps a chosen gesture to a specific Arduino pin
• Control — Arduino UNO interprets commands and distributes PWM signals to the servos
• Actuation — diymore ROT3U 6DOF arm; of its six servos the bottom and middle were driven to produce X/Y motion, each on a 6 V supply for stable torque

Results

• Median end-to-end response time: 820 ms from gesture to arm motion, over ten timed trials
• More training made classification worse. In EmotivBCI's dissimilarity view, well-separated training clusters are the goal — but each additional training set pulled the clusters closer until they overlapped entirely. We reversed the usual instinct and deliberately trained each gesture a minimal number of times so the classifier could still tell commands apart.
• Hair was the dominant noise source. It sat between scalp and electrode and produced erratic, weak signal acquisition. Once the primary test subject shaved his head, contact quality reached 100% across all sensors and signal quality held at a reliable 86% minimum — a large accuracy gain from a purely mechanical fix.
• Thought commands proved too unreliable to use. They demanded significant effort per command and registered inconsistently, so the final system used facial gestures exclusively.

Future Work

Drive all six joints including the clasper to complete a real task such as picking up an object or wiping a surface; take direct control of the EEG signal processing rather than relying on the vendor's classifier, to reduce sporadic behavior; and revise the control scheme so a movement can be halted before completion and multiple motors coordinated for more complex actions.

Fleet Reliability Engineering: Root Cause Analysis and a Python Data Pipeline

Reliability Engineer • Siemens Mobility • Jan 2025 – Present

Customer identity and fleet designation are omitted throughout.

Project Overview

Reliability engineering for a production fleet of safety-critical vehicles. The work splits into two halves: triaging individual failures down to a definite root cause, and building the data infrastructure that turns thousands of scattered test and failure records into something that predicts the next failure instead of just describing the last one. The second half is what moved the numbers.

Root Cause Analysis & Triage

Failures on an integrated vehicle arrive without a label. The diagnostic problem is deciding which layer actually broke:
• Wiring and cabling — harness faults, terminations, intermittent continuity
• Firmware and software — version mismatches between subsystems
• Configuration — a correct component set up wrongly for its role
• Component defect — genuine hardware failure
Isolating between these means correlating system logs, sensor data, and hardware/software traces from the same time window, because any one source alone is consistent with several of the four.

Data & Statistical Methods

• Analyzed fleet test and failure data in Python to surface recurring failure modes across the fleet rather than one vehicle at a time
• Applied SPC to distinguish real process shifts from ordinary variation
• Applied Weibull and MDBF analysis to characterize failure distributions and mean distance between failures
• Converted those findings into data-driven pass/fail criteria that catch component- and assembly-level defects before they escape to the field
• Built an automated Python + Power BI + Snowflake pipeline centralizing fleet test and failure data, automating customer deliverables and giving leadership real-time visibility into failure trends

Design-for-Reliability

Participated in design reviews during early development, applying DFMEA and FTA to push design-for-reliability and testability decisions upstream, where they are still cheap. Evaluated and executed ECO/ECR hardware changes with vendors and suppliers, expanding verification coverage each time to prevent regression.

Result

~60% fleet uptime improvement through permanent corrective actions — not workarounds, but changes that removed the failure mode. Customer reporting that had been assembled by hand became an automated pipeline.

Field Test Engineering: Emergency Brake Control Logic Optimization and Fault Analysis

Signal timing logic and reliability testing for a light rail vehicle platform

Customer identity, fleet designation, internal fault codes and exact timing parameters are omitted from this write-up.

Project Overview:

Collaborated with a cross-functional team to identify and resolve a recurring intermittent control fault on a light rail vehicle platform. Conducted field testing and analyzed logged fault data to isolate the operating conditions that produced inconsistent emergency-brake pushbutton signaling, which appeared predominantly in automatic operating mode. Recommended and validated a software timing adjustment that suppressed nuisance faults while preserving correct emergency-brake behavior. Coordinated test scheduling across teams and supported live troubleshooting in service, reducing fault incidents by over 50%.

Issue Background and Fault Diagnosis:

The fault was raised when the emergency-brake pushbutton was released slowly, producing a transient disagreement between redundant contacts that briefly interrupted a monitored trainline signal. Because the control logic evaluated contact agreement inside a short fixed monitoring window, a slow reset could fall outside that window and be logged as a fault even though the brake system itself was functioning correctly. Contributing factors included normal variation in how operators released the button, and mechanical wear or misalignment in the pushbutton assembly.

Proposed Solutions and Testing Strategy:

Proposed extending the de-energization delay on the pushbutton signal path so that the monitoring window tolerates ordinary variation in operator release time and minor mechanical inconsistency, without masking a genuine emergency-brake demand. Field testing reproduced the fault deliberately by holding and slow-releasing the button in automatic mode, which confirmed the diagnosis and ruled out a defect in the brake system itself. The timing change was validated in service and recommended for inclusion in a subsequent software release.

Field Test Engineering: Door Control Fault Resolution Through a Software-Driven Solution

Replacing a hardware modification with signal-conditioning logic on a light rail vehicle platform

Customer identity, fleet designation and internal fault codes are redacted from this write-up and from the diagrams below.

Project Overview:

A light rail vehicle fleet exhibited a recurring nuisance fault in its door control system originating in the original hardware design. A hardware modification intended to suppress the nuisance alert introduced a new functional fault that did affect vehicle operation. After extended troubleshooting, both faults were resolved in software, eliminating the need for any further hardware change — a lower-cost fix that could be deployed across the fleet far faster than a physical retrofit.

Fault Characterization:

The door system exhibited two distinct faults:
• Nuisance fault — a non-critical alert raised by the original door signal path, with no operational impact on the vehicle.
• Functional fault — introduced by the hardware modification, which caused certain door states to be misinterpreted and did affect vehicle operation.
Both were traced to inconsistencies in how door state signals were handled during specific door-disable operations, where observed behavior diverged from what the control logic expected across operating modes.

Issue Background and Fault Diagnosis:

Diagnosis isolated the contribution of the added hardware component by comparing door state reporting with and without it across every operating mode. The component altered the signal levels the control logic sampled, so a door-disable operation that was read correctly in one mode was interpreted as an invalid state in another. Bench and in-service testing narrowed the trigger to a specific sequence of door-disable operations rather than a random intermittent failure, which made the fault reproducible on demand and confirmed that the original hardware fix had traded a harmless alert for a functional one.

Proposed Solutions and Testing Strategy:

The team identified a software solution that filtered the spurious alert at its source: removing the added hardware component and implementing signal-conditioning logic to distinguish an intentional door-disable operation from an erroneous state. Testing validated that the software approach prevented both the nuisance and the functional fault with no hardware modification, and door state reporting was verified as correct across all operating modes before release.

Verilog Code for UART Transmitter


										
    module uart_tx (
    input wire clk,               // Clock input
    input wire rst_n,             // Active-low reset
    input wire [7:0] data_in,     // 8-bit parallel data
    input wire send,              // Signal to start transmission
    output reg tx,                // Serial data output
    output reg busy               // Transmission in progress indicator
);

    parameter BAUD_RATE = 9600;
    parameter CLK_FREQ = 50000000; // 50 MHz clock frequency

    localparam BIT_PERIOD = CLK_FREQ / BAUD_RATE;
    localparam IDLE = 2'b00, START = 2'b01, DATA = 2'b10, STOP = 2'b11;

    reg [1:0] state;
    reg [3:0] bit_index;
    reg [15:0] bit_counter;

    always @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            state <= IDLE;
            tx <= 1'b1;
            bit_index <= 4'b0;
            bit_counter <= 16'b0;
            busy <= 1'b0;
        end else begin
            case (state)
                IDLE: begin
                    busy <= 1'b0;
                    if (send) begin
                        state <= START;
                        busy <= 1'b1;
                    end
                end
                START: begin
                    tx <= 1'b0; // Start bit
                    if (bit_counter == BIT_PERIOD - 1) begin
                        bit_counter <= 0;
                        state <= DATA;
                    end else
                        bit_counter <= bit_counter + 1;
                end
                DATA: begin
                    tx <= data_in[bit_index];
                    if (bit_counter == BIT_PERIOD - 1) begin
                        bit_counter <= 0;
                        if (bit_index == 7)
                            state <= STOP;
                        else
                            bit_index <= bit_index + 1;
                    end else
                        bit_counter <= bit_counter + 1;
                end
                STOP: begin
                    tx <= 1'b1; // Stop bit
                    if (bit_counter == BIT_PERIOD - 1) begin
                        state <= IDLE;
                    end else
                        bit_counter <= bit_counter + 1;
                end
            endcase
        end
    end
endmodule

Sensor Fusion:Heat Tracking and Suppression

Tiva MCU Board — I2C, SPI and UART sensor integration in C

Objective:

The Heat-Triggered Fan project aims to enhance environmental comfort and energy efficiency through automated, responsive cooling based on ambient temperature readings.

Description:

This advanced system leverages sensor fusion technology to accurately monitor environmental conditions. Utilizing a combination of sensors communicating over I2C and UART interfaces, the system ensures precise temperature detection. When the ambient temperature exceeds a set threshold, the system activates a fan, efficiently mitigating heat without human intervention.

Sensor Fusion:

Employs multiple sensors via I2C and UART protocols for accurate temperature readings and reliable system performance. Automatic Activation: The fan is triggered automatically at a specific temperature threshold, maintaining consistent climate control. Energy Efficient: Operates the fan only when necessary, significantly reducing energy use. User-Friendly Interface: Allows users to easily adjust temperature thresholds and fan speeds according to their preferences. Functionality: At the core of the system is a microcontroller unit (MCU) that orchestrates all operations. It processes inputs from digital thermostats connected through I2C and additional sensors interfaced via UART. This dual communication strategy enhances the reliability and accuracy of the temperature readings, forming a solid basis for the activation logic of the fan.

Features

Enhanced Comfort: Automatically keeps indoor environments at a comfortable temperature. Cost-Effective: Lowers energy bills by optimizing when and how the fan is used. Environmentally Friendly: Improves energy efficiency, contributing to a lower carbon footprint. Technical Innovation: Integrates sophisticated sensor and communication technologies to provide a cutting-edge solution to climate control. Applications: This system is particularly suited for residential homes, offices, and industrial settings where maintaining a set temperature efficiently is crucial.

Conclusion:

The Heat-Triggered Fan project represents a significant advancement in smart climate control technologies. By integrating precise sensor fusion with sophisticated MCU management over I2C and UART interfaces, it delivers a highly effective, energy-efficient cooling solution that enhances both comfort and environmental sustainability.

										void I2C1_Init( void ){
											SYSCTL->RCGCGPIO  |= 0x01 ; // Enable the clock for port A
											SYSCTL->RCGCI2C   |= 0x02 ; // Enable the clock for I2C 1
											GPIOA->DEN |= ( 1 << 6 | 1 << 7); // Assert DEN for port A
											// Configure Port A pins 6 and 7 as I2C1
											GPIOA->AFSEL |= 0xc0 ;
											GPIOA->PCTL |= 0x33000000 ;
											GPIOA->ODR |= (1<<7) ; // SDA (PA7 ) pin as open darin
											GPIOA->AMSEL &= ~( 1 << 6 | 1 << 7);
											I2C1->MCR  = 0x0010 ; // Enable I2C 3 master function
											/* Configure I2C 3 clock frequency
											(1 + TIME_PERIOD ) = SYS_CLK /(2*
											( SCL_LP + SCL_HP ) * I2C_CLK_Freq )
											TIME_PERIOD = 16 ,000 ,000/(2(6+4) *100000) - 1 = 7 */
											I2C1->MTPR  = 0x07 ;
										}
										
										/* wait untill I2C Master module is busy */
										/*  and if not busy and no error return 0 */
										static int I2C1_wait_till_done(void)
										{
											while(I2C1->MCS & 1);   /* wait until I2C master is not busy */
											return I2C1->MCS & 0xE; /* return I2C error code, 0 if no error*/
										}
										
										int I2C1_Write_Multiple(int slave_address, char slave_memory_address, int bytes_count, uint8_t * data)
										{   
											int error;
											if (bytes_count <= 0)
												return -1;                  /* no write was performed */
											/* send slave address and starting address */
											I2C1->MSA = slave_address << 1;
											I2C1->MDR = slave_memory_address;
											I2C1->MCS = 3;                  /* S-(saddr+w)-ACK-maddr-ACK */
										
											error = I2C1_wait_till_done();   /* wait until write is complete */
											if (error) return error;
										
											/* send data one byte at a time */
											while (bytes_count > 1)
											{
												I2C1->MDR = *data++;             /* write the next byte */
												I2C1->MCS = 1;                   /* -data-ACK- */
												error = I2C1_wait_till_done();
												if (error) return error;
												bytes_count--;
											}
											
											/* send last byte and a STOP */
											I2C1->MDR = *data++;                 /* write the last byte */
											I2C1->MCS = 5;                       /* -data-ACK-P */
											error = I2C1_wait_till_done();
											while(I2C1->MCS & 0x40);             /* wait until bus is not busy */
											if (error) return error;
											return 0;       /* no error */
										}
										
										
										int I2C1_read_Multiple(uint8_t slave_address, char slave_memory_address, int bytes_count, uint8_t * data)
										{
											int error;
											
											if (bytes_count <= 0)
												return -1;         /* no read was performed */
										
											/* send slave address and starting address */
											I2C1->MSA = slave_address << 1;
											I2C1->MDR = slave_memory_address;
											I2C1->MCS = 3;       /* S-(saddr+w)-ACK-maddr-ACK */
											error = I2C1_wait_till_done();
											if (error)
												return error;
										
											/* to change bus from write to read, send restart with slave addr */
											I2C1->MSA = (slave_address << 1) + 1;   /* restart: -R-(saddr+r)-ACK */
										
											if (bytes_count == 1)             /* if last byte, don't ack */
												I2C1->MCS = 7;              /* -data-NACK-P */
											else                            /* else ack */
												I2C1->MCS = 0xB;            /* -data-ACK- */
											error = I2C1_wait_till_done();
											if (error) return error;
										
											*data++ = I2C1->MDR;            /* store the data received */
										
											if (--bytes_count == 0)           /* if single byte read, done */
											{
												while(I2C1->MCS & 0x40);    /* wait until bus is not busy */
												return 0;       /* no error */
											}
										 
											/* read the rest of the bytes */
											while (bytes_count > 1)
											{
												I2C1->MCS = 9;              /* -data-ACK- */
												error = I2C1_wait_till_done();
												if (error) return error;
												bytes_count--;
												*data++ = I2C1->MDR;        /* store data received */
											}
										
											I2C1->MCS = 5;                  /* -data-NACK-P */
											error = I2C1_wait_till_done();
											*data = I2C1->MDR;              /* store data received */
											while(I2C1->MCS & 0x40);        /* wait until bus is not busy */
											
											return 0;       /* no error */
										}

Enclosed Mushroom Eviroment Control System IOT Project

Project Overview:

Our aim is to craft a system that not only talks to mushrooms in their language - humidity, temperature, and CO2 - but also listens to them, adjusting their environment to help them thrive. This isn’t just a control system; it's a cultivation companion for gourmet mushroom aficionados on a budget.As inflation rises, so do food prices and the amount of hours worked required to acquire your food. Furthermore, there is less and less space for the production of food in major cities where food demand and waste is highest. With the way that our economy is going it would not be unreasonable to think that we will soon find ourselves in another recession and unable to purchase luxury items like gourmet mushrooms.

Design & Testing:

• Humidity sensor — measures water vapor content inside the enclosed system.
• Temperature sensor — measures ambient temperature to keep the chamber in range.
• CO2 & O2 sensor — detects the amount of CO2 and O2 present in the system.
• Relay control — drives the environmental actuators, triggering the humidifier to raise humidity or opening a vent to raise O2.
• LCD user interface — lets the user cycle through and read each measured parameter.
